# shk-wb.ru — сайт, две программы для ПВЗ и Telegram-бот

Один репозиторий на всё: сайт и API (`src/`, `api/`, `server/`, `selfhost/`), Telegram-бот (живёт внутри
серверного процесса сайта, отдельного деплоя у него нет) и серверная половина двух настольных программ
для пунктов выдачи WB. Сами программы лежат в `_local-only/` — эта папка в `.gitignore`, её исходники
и сборки переносятся и публикуются отдельно.

## Сервер и выкладка

- Сервер: `root@212.193.59.72`, ключ `~/.ssh/shk-wb_ed25519`. Переменные — `/srv/shk-wb/.env`
  (перед правкой `cp .env .env.bak-$(date +%s)`), перезапуск — `systemctl restart shk-wb`.
- Выкладка сайта: `SSH_OPTS="-i ~/.ssh/shk-wb_ed25519" bash selfhost/deploy.sh root@212.193.59.72` (~3 мин).
  Push в `main` тоже выкладывает через GitHub Actions, но это 15–20 мин.
- Установщики программ — `/srv/shk-wb/app-updates/{pvz-helper,cell-print}/`, публичные ссылки https://shk-wb.ru/dl/.
- Миграции: `npx supabase db query --linked -f <файл>` (история миграций в Supabase не ведётся).
- **Менялась только программа — сайт не выкладывать.** Но если программа ждёт нового эндпоинта, выкладка
  обязательна: иначе выпуск неполный и обновление у людей не работает (так вышло с «Печатью ячеек» 2.1.0).

## ЖЕЛЕЗНОЕ ПРАВИЛО: клиент не выпускается раньше своего сервера

**Если программа начинает ходить в новый эндпоинт — сервер с этим эндпоинтом выкладывается ПЕРВЫМ,
и это проверяется запросом к боевому домену, а не «написано и ладно».** Серверная половина никогда
не остаётся в побочной ветке: прод едет ТОЛЬКО из `main`, и `deploy.sh` отказывается работать
из другой ветки или при грязном дереве — **обход `ALLOW_NON_MAIN=1` запрещён**. Нужна выкладка
из ветки — сначала влить ветку в `main`.

Перед выпуском любой программы, которая обращается к серверу, обязательны три шага:
1. `git log --oneline main..<ветка>` — убедиться, что серверных кусков фичи не осталось в ветке;
2. `curl -s -o /dev/null -w "%{http_code}" https://shk-wb.ru/<новый путь>` — ответ НЕ 404
   (помнить: новый `/api/...` без строки в `vercel.json` даёт голый `404: NOT_FOUND`, и программа
   покажет безликое «Ошибка сервера (404)» — в таком ответе нет поля `error`);
3. `ls -l /srv/shk-wb/current` на сервере — сверить, что живой релиз это тот, что вы и думаете,
   ПЕРЕД тем как запускать `deploy.sh` (иначе затрёте чужую выкладку).

Код выхода деплоя смотреть у самого скрипта: `bash selfhost/deploy.sh … > log 2>&1; echo $?`.
Через `| tail` код приходит от `tail` и всегда равен 0 — выкладка может молча не состояться.

Цена нарушения (29.10.2026, три случая за сутки): «Печать ячеек» 2.1.0 выпущена с проверкой
обновлений через `/api/cell-print/update`, которого на сервере не было → автообновление не работало
ни у кого; «Помощник ПВЗ» 1.6.6 выпущен с запросом QR к `/api/app/qr-image`, которого на сервере
не было → у людей «Ошибка сервера (404)» вместо кода клиента; деплой из `main` затёр редизайн,
выложенный из другой ветки в обход защиты.

## Общие правила

- Проверки кода: `cargo check --lib` в `src-tauri`, TypeScript и Vite build в Tauri-проекте, `npm test` в корне.
  Vitest ограничен тестами `src/`, чтобы не захватывать соседний черновой проект.
- Ошибки чтения и сохранения не маскировать бесконечной загрузкой или ложным успехом; у главных окон Tauri
  и «Печати ячеек» есть аварийный экран с перезапуском. При добавлении новых асинхронных экранов всегда
  разделять состояния `loading`, `empty` и `error`.
- Актуальную версию программы определять по `src-tauri/tauri.conf.json` / `Cargo.toml`, а не по старому README.
  Для «Печати ячеек» сверять ещё и с живой лентой — подробности в `docs/cell-print.md`.
